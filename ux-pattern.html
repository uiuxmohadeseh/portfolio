Task-Based UX Pattern Library

Context

We were working across a diverse portfolio of interconnected enterprise products, each dealing with large volumes of data, complex workflows, and different business rules.

Our Design System provided a shared visual language across products. However, components and variants alone were not enough to standardize how interaction problems should be solved.

As a result, similar user problems could be implemented with different interaction models and behaviors across different products.

We needed a layer beyond individual components—one that would define not only what to build , but also when, how, and why a particular UX pattern should be used .

This led to the idea of a Task-Based UX Pattern Library : a reusable layer of interaction patterns organized around common user tasks and workflow scenarios rather than individual UI components.

The goal was to create greater consistency at the behavioral and interaction level , while still allowing individual products to adapt patterns to their specific business context.

Problem & Challenges

As our products grew in scope and complexity, I noticed that similar problems were being solved with different interaction patterns across different parts of the system.

This created a recurring question whenever we designed a new feature:

“Which existing pattern should this feature follow?”

There was no single, reliable answer.

A significant amount of design time was spent searching for similar use cases, reviewing previous solutions, and making design decisions for problems we had already encountered elsewhere in the product.

The problem went beyond design efficiency. A new solution might improve the UX of an individual feature, but if it introduced a new interaction model, it could also create a new behavior that existing users had to learn.

In other words, improving one feature did not necessarily mean improving the overall product experience.

The impact extended beyond the Design team

With every new release, Support and Implementation teams also had to spend time explaining new behaviors, training users, and answering questions caused by inconsistencies across the product.

From the users’ perspective, encountering different interaction patterns for similar tasks increased the learning curve. Even after being trained on a process or having used it before, users could still need support when performing a similar task elsewhere in the system.

Over time, what initially looked like a design consistency problem became a product-scale problem involving design efficiency, usability, support effort, and long-term scalability.

The question was no longer simply:

“How can we make the UI more consistent?”

The more important question became:

“How can we create repeatable design decisions and predictable product behaviors for similar problems—without designing every feature from scratch?”

Key Challenges

01 — No clear reference for design decisions

There was no centralized reference for determining which existing pattern should be used for a particular scenario.

02 — Re-solving recurring problems

Designers repeatedly explored and evaluated solutions for problems that had already been solved elsewhere in the product.

03 — Inconsistent product behavior

Different solutions to similar problems resulted in different interaction behaviors across products and workflows.

04 — Increased learning effort for users

Even when a new feature provided a better UX, introducing a different interaction pattern could force users to learn a new way of completing a familiar task.

05 — Increased dependency on Support & Implementation

New behaviors and inconsistencies required additional explanation and training, increasing the operational effort required to support users.

06 — An increasingly unscalable design process

As the number of products and features grew, continuously making these decisions from scratch increased design effort and contributed to Design Debt .

The Shift in Thinking

These challenges led me to look beyond individual features and components.

Instead of asking:

“What is the best solution for this feature?”

I started asking:

“Can we identify recurring user tasks and define reusable interaction patterns around them?”

This became the starting point for exploring a Task-Based UX Pattern Library —a system for documenting not just reusable UI elements, but the decision logic, usage context, interaction behavior, and rationale behind recurring UX patterns.

Task-Based Approach

By analyzing the challenges across our products, I realized that the problem was not simply a lack of Components—or even a lack of Patterns.

The deeper problem was the absence of a clear framework for deciding which Pattern should be used in a given situation.

To address this, I shifted the starting point of the design process from the UI itself to the work the user is trying to accomplish .

Instead of starting with Components, I first identified the user's Task , then defined the appropriate interaction Pattern and the Components required to support it.

The design approach shifted from:

Feature → Component → UI

to:

Task → User Goal → UX Pattern → Component

This helped us establish a consistent decision-making process before designing a new feature:

1. What is the user trying to accomplish? 2. What type of Task is this? 3. What interaction model best supports this Task? 4. Do we already have a Pattern for this scenario? 5. Which Components are needed to implement that Pattern?

This approach allowed us to move from component-driven design to task-driven interaction design.

Task Taxonomy

To make this approach usable across products, I reviewed recurring user activities and grouped them based on the user's goal and the nature of the work being performed.

01 — Transactional Tasks

Tasks where the primary goal is to create, submit, complete, or change the state of an entity or process.

Examples:

Entering information

  • Creating a record
  • Completing a process Approving or submitting information
  • Performing an action on an entity

The primary focus in this category is successful task completion with minimal errors.

02 — Monitoring Tasks

Tasks where the user's primary goal is to understand status, monitor progress, or track changes across one or more entities.

Examples:

Viewing request statuses

  • Tracking ongoing processes
  • Identifying items that require action

Reviewing changes over time

Unlike transactional tasks, users in this category primarily consume and interpret information rather than create it.

03 — Reactive & Exception Tasks

Tasks triggered by an error, warning, restriction, deadline, or unexpected condition.

Examples:

Responding to a system error

  • Handling an invalid state
  • Taking action when a deadline is approaching
  • Resolving an exceptional condition

In these scenarios, the system first communicates that something requires attention, and the user then takes an appropriate action to resolve or manage it.

04 — Communication, Collaboration & Coordination Tasks

Tasks focused on transferring information, coordinating people or teams, and facilitating collaboration around a process or entity.

Examples:

Assigning or referring an item to another person or team

  • Managing approvals across different roles
  • Exchanging information
  • Coordinating activities between participants in a workflow

Success in this category depends largely on alignment between people and accurate information transfer.

05 — Planning & Scheduling Tasks

Tasks where users need to organize future activities, resources, events, or process steps.

Examples:

  • Scheduling an event or meeting

Setting activity dates

  • Planning upcoming workflow stages
  • Managing milestones and deadlines

The primary focus is on time, sequence, dependencies, and coordination.

06 — Data Management Tasks

Tasks focused on finding, organizing, selecting, editing, or extracting information from a dataset.

Examples:

Searching for a record

  • Filtering data
  • Managing lists
  • Editing information
  • Selecting multiple records
  • Exporting data

In this category, users primarily work with collections of data , making discoverability, information density, and efficient data manipulation particularly important.

From Taxonomy to Design Decisions

The taxonomy introduced a higher-level decision layer between the user's goal and the UI implementation.

Task defines what the user is trying to accomplish. Pattern defines how that task should be performed. Components provide the building blocks for implementing the Pattern.

For example:

  1. Data Management Task User Task
  2. Select multiple items from a dataset
  3. UX Pattern Bulk Selection
  4. Components

Table + Checkbox + Search + Filter + Action Bar

  1. Transactional Task User Task
  2. Enter complex information
  3. UX Pattern Structured Form
  4. Components Input + Select + Validation + Action Bar

This structure changed the role of Components in the design process.

Components were no longer the starting point for interaction decisions. They became implementation building blocks within a larger UX Pattern.

This distinction was important because it allowed us to standardize behavior and interaction logic , rather than simply standardizing the visual appearance of the interface.

UX Pattern Library

Once the Task Taxonomy was established, the next step was to identify and document the interaction patterns that best supported each type of Task.

Finding Patterns Without Product Analytics

At this stage, we faced an important constraint: our existing products did not have sufficient product analytics or quantitative behavioral data to reliably identify where users were struggling.

Instead of relying on analytics, we used qualitative evidence and the experience of teams working closely with users .

We interviewed Support and Implementation teams and reviewed how users interacted with existing products. This helped us identify areas where users frequently experienced confusion, ambiguity, or difficulty completing a process.

At the same time, we looked for interactions that users were able to understand and complete with little or no training or assistance.

This comparison helped us identify both successful and problematic interaction patterns from real product usage and understand which types of solutions worked better in which contexts.

From Tasks to Patterns

We then mapped relevant interaction patterns to each Task category and organized them into a centralized UX Pattern Library .

However, the goal was not to create another collection of UI examples.

For each Pattern, we documented the decision logic behind it:

  • When should it be used? When should it not be used?
  • What rules should be followed when applying it?
  • Which types of Tasks does it support?

This transformed the Pattern Library from a simple design reference into a decision-making framework .

When designing a new feature, designers could first identify the underlying Task, explore the relevant Patterns, and select an appropriate interaction model based on the context—instead of inventing a new solution from scratch.

The Decision Model

  1. User & Team Feedback
  2. Identify Pain Points & Successful Interactions
  3. Task Type
  4. Relevant UX Patterns
  5. When to Use / When Not to Use
  6. UX Rules
  7. Reusable Design Decisions

The goal was not to force one fixed solution for every problem .

Instead, we wanted to establish a shared language for making design decisions—so that similar problems, in similar contexts, could be solved using similar interaction logic.

This became the foundation for creating more predictable product behavior while giving designers a reusable framework for making and communicating UX decisions.

From Feature to Pattern

To demonstrate how the Task-Based approach works in practice, consider a common feature such as “Create Request.”

Note: This is a simplified example used to illustrate the approach.

Although “Create Request” appears to be a single feature, completing it involves several different user Tasks. Each Task has a different goal and interaction requirement, so the appropriate UX Pattern is selected based on the nature of the Task.

User taskUX patternTask type
Enter basic informationSectioned FormTransactional
Add applicantsEditable Data GridTransactional
Add documentsSelection Table / Table-based PatternTransactional
Review request informationContext Header / Detail ViewMonitoring
Validate informationInline ValidationReactive
Confirm submissionConfirmation / Action PatternReactive

This means we don't choose a Pattern based simply on the feature itself. We break the feature down into the Tasks users need to perform, then select Patterns based on the characteristics of each Task.

Example: Adding Applicants

One of the Tasks within the “Create Request” feature is adding one or more applicants .

At first glance, this might seem like a simple selection problem. However, the actual Task is more complex.

A request may have multiple applicants, and users may need to:

  • Add multiple records. View information for each applicant.
  • Enter or complete additional information.

Edit individual applicant records.

A simple Dropdown or Autocomplete would not adequately support this Task.

A Selection Table , on the other hand, is more appropriate when the primary goal is simply to select one or more existing items.

In this scenario, the user needs to create or complete multiple similar records and directly manage multiple editable values for each record.

Therefore, the appropriate Pattern is an Editable Data Grid .

  1. Design Decision Create Request
  2. Add Applicants
  3. Multiple records + multiple editable values
  4. Editable Data Grid

With this Pattern, each applicant is represented as an independent row, with the required information entered or edited directly within that row.

Pattern Rule

Use an Editable Data Grid when users need to manage multiple similar records with multiple editable attributes within a tabular structure—not when the primary goal is simply to select one or more existing items.

This distinction is important because it turns the Pattern Library into more than a collection of UI examples. It provides a rule-based way to choose between similar interaction patterns based on the user's Task and goal.

Pattern Relationships

At the next stage, I realized that selecting a single Pattern was not always enough to support a Task. In complex enterprise products, users often perform multiple types of interactions sequentially or simultaneously to complete a single activity.

This meant that Patterns needed to be defined not only as standalone solutions, but also through their relationships and composability with other Patterns .

For example, within the same Create Request feature, a user may need to enter information, add multiple applicants, correct validation errors, and finally submit the request. Each part of this flow may require a different Pattern:

Create Request
  1. 1Sectioned Form
    In-page Navigation
  2. 2Add Applicants
    Editable Data GridInline Validation
  3. 3Add Documents
    Selection Table
  4. 4Final Submission
    ConfirmationNotification

In this structure, Patterns do not replace one another. Instead, they work together to form a complete Workflow .

A Practical Example

Consider a long information form where users need to add an unknown number of applicants. A suitable combination of Patterns could be:

  1. Sectioned Form For organizing information into logical sections
  2. In-page Navigation For providing quick access to different sections of the form
  3. Editable Data Grid For managing multiple applicants
  4. Inline Validation For displaying errors directly within the relevant row or field
  5. Notification For communicating the outcome of the submission

The important point is that each Pattern has a distinct role within the overall interaction model.

Rules for Pattern Relationships

To prevent inappropriate combinations, defining When to Use is not enough. Each Pattern also needs to define which other Patterns it can be combined with and under what conditions .

Should

Combine Patterns based on actual Task requirements.

Use Patterns that complement each other rather than duplicating the same interaction.

  • Make the hierarchy and role of each Pattern clear to the user.
  • Ensure that combining Patterns does not unnecessarily increase Workflow complexity.

Should Not

Combine multiple Patterns simply to cover every possible capability.

  • Use two Patterns with overlapping functionality within the same interaction.
  • Apply a Pattern outside of its appropriate context.
  • Create multiple paths for completing the same Action as a result of combining Patterns.

The Goal

The purpose of defining Pattern Relationships is not to create a fixed template for every Feature. Instead, it is to establish:

What role does each Pattern play within a Workflow, and under what conditions can it work alongside other Patterns?

This approach transforms the Pattern Library from a collection of independent Patterns into a composable system for designing complex Workflows .

Rather than prescribing a single solution for an entire Feature, the library provides a framework for combining interaction models intentionally—based on the user's Task, the context, and the role each Pattern plays within the overall Workflow.

Version History

We did not treat the Pattern Library as a static collection of rules and components. Instead, we designed it as a living system that could evolve with real product usage.

Each Pattern was initially defined based on the evidence, constraints, and experience available at the time. However, applying a Pattern across real products could reveal new insights: a solution that worked well in one context might introduce unnecessary complexity or confusion in another.

For this reason, feedback from users and product teams became part of the Pattern lifecycle.

A Pattern review could result in a minor change to an existing UX Rule—or a more fundamental change to the Pattern itself, including its structure, supporting Components, or even its replacement with a different interaction model.

Versioning gave us a controlled way to track these changes and understand:

What changed?

  • Why did it change?
  • What is different from the previous version?

What evidence led to the decision?

An Example

Imagine that an Editable Data Grid is initially selected for a recurring Task:

  1. v1.0 Editable Data Grid
  2. Managing multiple similar records

After the Pattern is used in a real product, user feedback reveals that each record requires additional information and interactions. Placing all of this information directly inside table cells makes the rows difficult to scan and increases the likelihood of errors.

Instead of simply changing the Pattern's rules, we may need to reconsider the interaction model itself:

  1. v1.0 Editable Data Grid
  2. Inline Editing
  3. High complexity within each row

v2.0 Editable Data Grid

  1. Row Detail / Expanded Form
  2. Complex information handled outside the cells

The Pattern has evolved based on evidence from real usage rather than being treated as a fixed design rule.

Version History was not just a record of changes; it was part of how Patterns evolved.

Each Pattern could be revisited based on user feedback, real-world product usage, changes in the Design System, and emerging business requirements.

The history allowed the team to understand how a design decision evolved over time— what changed, why it changed, and when the Pattern needed to be refined, extended, or replaced.

This turned the Pattern Library from a static documentation artifact into a living design system that could learn from product usage and continuously improve.

Impact

Implementing the Task-Based UX Pattern Library removed a significant portion of repetitive design decisions from individual projects, allowing the team to focus on the core problem behind each Feature rather than repeatedly redefining interaction solutions.

1. Faster Design Decisions

For many recurring Tasks, designers no longer had to determine the interaction model from scratch. Once the Task, relevant Patterns, and usage rules were clear, the decision-making process became much more direct.

Result: Less time was spent searching for references, comparing alternative solutions, and revisiting recurring design decisions, enabling Features to move through the design process faster.

2. Faster Development

With interaction Patterns and their underlying rules already defined, the gap between Design and Development was reduced. Instead of encountering a completely new UI solution for each Feature, developers worked with Patterns whose structure and behavior had already been established.

Result: Implementation ambiguity decreased, reducing back-and-forth between Design and Development and making Feature development more predictable.

3. More Consistent User Experience

The Pattern Library reduced the number of different solutions being created for similar Tasks. As a result, users encountered more familiar interaction behaviors across different areas of the products.

Result: Users spent less effort relearning how similar interactions worked, making the overall experience more predictable and consistent.

4. Reduced Dependence on Individual Decision-Making

UX decisions were no longer limited to a designer's individual knowledge or buried within Figma files. They became reusable knowledge that could be shared and applied across the team.

Result: The team could make decisions based on a shared framework and reuse established Patterns across new Features and projects.

5. A Foundation for Scaling the Design System

The Design System established a shared visual language at the Component level. The Pattern Library extended this system to the level of UX behavior and decision-making .

The Design System defined what to build; the Pattern Library helped define when, why, and how to use it.

Together, they created a more scalable foundation for maintaining consistency—not only in how the products looked, but also in how they behaved.

Learnings

This project changed the way I think about Design Systems —from a collection of reusable Components into a broader design decision-making system .

One of my biggest learnings was that standardization is valuable only when it balances Consistency with flexibility and the ability to evolve . Patterns should not be treated as fixed rules. They need to evolve based on evidence from real-world usage, user feedback, and changing product needs.

I also learned that documenting design decisions creates the most value when it becomes shared, actionable knowledge for the entire team , rather than simply serving as a reference document for designers.

Ultimately, the Pattern Library taught me that a scalable Design System is not just about creating reusable building blocks. It is about creating a shared language for making, communicating, and revisiting design decisions across products and teams.
