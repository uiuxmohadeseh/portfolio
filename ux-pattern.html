Why the library was needed

Our Design System aligned the look of enterprise products, but similar tasks still behaved differently.

The products shared complex workflows, large datasets, and different business rules. Components and variants provided a visual language, but not a shared reference for deciding when, how, and why to use an interaction pattern.

No clear decision reference

Designers had no centralized answer to “Which pattern fits this scenario?”

Recurring problems solved again

Time went into finding precedents, comparing solutions, and revisiting decisions already made elsewhere.

Inconsistent product behavior

Similar tasks could follow different interaction models across products and workflows.

More learning for users

An improvement to one feature could introduce unfamiliar behavior in an otherwise familiar task.

More support and training effort

Support and Implementation teams had to explain new behaviors and train users around inconsistencies.

A process that was hard to scale

Repeated decisions increased design effort and Design Debt as products and features grew.

The design question

How could we make recurring design decisions reusable and product behavior predictable, while allowing patterns to adapt to each product’s business context?

Finding patterns without analytics

The available evidence was qualitative: Support and Implementation interviews, team experience, and existing product usage.

The products did not have sufficient analytics or quantitative behavioral data to reliably locate user difficulties. We interviewed the teams closest to users and reviewed existing interactions, looking at both recurring confusion and tasks completed with little or no training.

Where users struggled

Ambiguity, confusion, and difficulty completing a process helped identify problematic interaction patterns.

Where interactions already worked

Tasks understood with little assistance provided useful precedents, rather than assuming every solution needed to be redesigned.

Comparing these interactions helped us understand which solutions worked in which contexts. We mapped relevant patterns to task categories and documented their decision logic in a centralized library.

Six types of user tasks

I grouped recurring activities by the user’s goal and the nature of the work, rather than by a feature or component name.

01

Transactional

Create, submit, complete, or change the state of an entity or process.

Examples
Information entry, record creation, process completion, approval, submission, or an action on an entity.
Design focus
Successful completion with minimal errors.
02

Monitoring

Understand status, progress, or changes across entities.

Examples
Request statuses, ongoing processes, items needing action, and changes over time.
Design focus
Help users read and interpret information rather than create it.
03

Reactive & exception

Respond to an error, warning, restriction, deadline, or unexpected condition.

Examples
System errors, invalid states, approaching deadlines, and exceptional conditions.
Design focus
Make the need for attention clear and support the appropriate response.
04

Communication, collaboration & coordination

Transfer information and coordinate people or teams around a process.

Examples
Assignment, referral, approvals across roles, information exchange, and workflow coordination.
Design focus
Alignment between people and accurate information transfer.
05

Planning & scheduling

Organize future activities, resources, events, or process steps.

Examples
Meetings, activity dates, future workflow stages, milestones, and deadlines.
Design focus
Time, sequence, dependencies, and coordination.
06

Data management

Find, organize, select, edit, or extract information from a dataset.

Examples
Search, filters, list management, editing, multi-selection, and data export.
Design focus
Discoverability, information density, and efficient data manipulation.

How a task becomes a design decision

The starting point became the work the user needed to accomplish. Components supported the chosen pattern, rather than defining the interaction.

  1. TaskWhat is the user trying to do?
  2. User goalWhat does successful completion mean?
  3. UX patternWhich interaction model fits this task and context?
  4. ComponentsWhich building blocks implement that pattern?

Before designing a feature, we identified its tasks and task types, checked for an existing pattern, and selected the required components. This standardized interaction logic as well as appearance.

TaskUX patternSupporting components
Data management: select multiple items from a datasetBulk SelectionTable, Checkbox, Search, Filter, Action Bar
Transactional: enter complex informationStructured FormInput, Select, Validation, Action Bar

What each pattern documented

  • The task types it supports.
  • When to use it and when not to use it.
  • The UX rules that guide its application.
A decision framework, not a fixed template

Similar problems in similar contexts should share interaction logic. The library provided a common language for choosing and communicating a solution, without forcing one answer onto every product.

A worked example: Create Request

Simplified example from the original case study

One feature contains several tasks. Each task needs an interaction pattern suited to its goal.

User taskUX patternTask type
Enter basic informationSectioned FormTransactional
Add applicantsEditable Data GridTransactional
Add documentsSelection Table / Table-based PatternTransactional
Review request informationContext Header / Detail ViewMonitoring
Validate informationInline ValidationReactive
Confirm submissionConfirmation / Action PatternReactive

Why “Add Applicants” needs an Editable Data Grid

Users may need to add several applicants, view each record, complete additional information, and edit values independently. Each applicant is represented as a row, with the required information entered or edited within that row.

OptionFit for this task
Dropdown / AutocompleteInsufficient for creating or completing multiple records with several editable values.
Selection TableAppropriate when the goal is to select one or more existing items.
Editable Data GridAppropriate for managing multiple similar records with multiple editable attributes in a table.
The selection rule

Choose the pattern from the task and goal, not from the feature name. Selecting existing items and managing editable records are different interaction needs.

Combining patterns into a workflow

A complex activity may need several patterns working together, each with a distinct role.

In Create Request, entering information, adding applicants, correcting errors, and submitting are connected tasks. Patterns complement one another rather than replace one another.

Create Request
  1. 1Sectioned Form
    In-page Navigation
  2. 2Add Applicants
    Editable Data GridInline Validation
  3. 3Add Documents
    Selection Table
  4. 4Final Submission
    ConfirmationNotification
  • Sectioned Form organizes the information; In-page Navigation provides quick access to its sections.
  • Editable Data Grid supports an unknown number of applicants; Inline Validation places errors beside the relevant field or row.
  • Selection Table supports document selection; Confirmation and Notification support final submission and its outcome.

Combine intentionally

Use actual task requirements, choose complementary patterns, make their roles and hierarchy clear, and avoid unnecessary workflow complexity.

Avoid overlap

Do not add patterns to cover every possible capability, duplicate an interaction, use a pattern outside its context, or create competing paths for the same action.

Documenting when to use a pattern was not enough: the library also needed to describe which patterns it could work alongside and under what conditions.

Keeping patterns open to change

Version history recorded what changed, why, how it differed, and which evidence informed the decision.

Feedback from users and product teams could lead to a small UX-rule refinement, a structural change, different supporting components, or a replacement interaction model. Product usage, Design System changes, and new business requirements could all trigger a review.

Illustrative example · not a measured project result

Starting point: inline editing

Imagine an Editable Data Grid for multiple similar records. More information and interactions make its rows hard to scan and increase the risk of errors.

Reconsidered model: row details

A later version could move complex information into Row Detail / Expanded Form, rather than placing everything inside table cells.

Qualitative impact and learnings

Qualitative outcomes · no quantified measures provided

The library moved recurring interaction decisions into shared, reusable knowledge.

Faster design decisions

A known task, relevant patterns, and clear usage rules reduced repeated reference searches, solution comparisons, and decisions made from scratch.

Faster, more predictable development

Established structures and behaviors reduced implementation ambiguity and back-and-forth, helping development move faster.

More familiar product behavior

Fewer different solutions for similar tasks meant less relearning and a more consistent experience across products.

Less dependence on individual knowledge

Decisions became accessible beyond a designer’s memory or Figma file and could be reused across projects and teams.

A foundation for scaling the Design System

The component system described what to build; the pattern library added when, why, and how to apply it, extending consistency into behavior.

My main learning

A scalable Design System needs a shared language for making and revisiting decisions. Standardization works when it balances consistency with flexibility, and documentation becomes actionable knowledge for the whole team.
